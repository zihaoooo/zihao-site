Slope Mesh
A surface is a function. Every point has a position, a normal vector, and a slope. You will write a Grasshopper Python script that queries your WF04 Patch surface and colors it by slope — not from scratch, but by specifying what you want precisely enough that Claude can write it.
The central skill is converting intention into specification. Students who get bad scripts back under-specified the geometry.
Part 2 removes the carrying. You install an MCP bridge so Claude works inside Rhino directly, reading your model and checking its own results.
Part 1 Specify It, Then Carry the Code
01 Understand the Geometry In class — no computers
Answer these in plain English before opening Claude.
  • How do you locate a point on a surface? UV parameters — two numbers addressing any point in the surface domain.
  • How do you ask a surface which way it faces? The normal vector — perpendicular to the surface at that UV location.
  • How do you measure slope from a normal? Angle between the normal and world Z. Flat = 0°, vertical = 90°.
  • What counts as steep in landscape terms? Walkable. Wheelchair-accessible. Water-shedding. Design thresholds, not arbitrary numbers.
02 Interview Claude to Build Your Spec CHAT
Open a new Claude chat. Paste this starter prompt exactly:
I'm a landscape architecture student working in Rhino 8 Grasshopper. I want to write a Python script that analyzes my surface. Before writing any code or spec, interview me one question at a time to understand exactly what I need. Do not write code yet. Do not move to the next question until I answer.
Answer each question. Push visual answers ("I want it to look like…") toward geometric ones ("the script needs to measure…").
After the last question, Claude summarizes the spec — inputs, outputs, color scale, edge cases. Review it. Confirm and ask Claude to write the script. Everything stays in one conversation.
The spec is a deliverable — copy it out of the chat when you're done.
Example: Sample interview + spec chat
03 Set Up the Python Component GH
Add a Python 3 Script component. Use the input and output names from your Stage 2 spec — Claude's script will list them as comments at the top.
  • Inputs — one per geometry or parameter the script needs
  • Output — one per result
⚠
Right-click each input and set the type hint. Without this, Grasshopper passes GUIDs instead of geometry and the script errors immediately. Outputs don't need a type hint.
Wire inputs to geometry and parameters already on your canvas.
04 Execute and Debug CHAT GH
Ask Claude to write the script. Paste it into the Python component and hit Run. The loop — run, error, fix — is normal.
  • Errors: copy the full error message and paste it back to Claude.
  • Wrong output: screenshot and describe what you see.
Common issues
  • Errors immediately → type hints not set on inputs
  • Colors flipped → tell Claude; it will fix the normal direction
  • Mesh doesn't appear → viewport must be in Shaded mode; output wired to a Mesh parameter
Part 2 Give Claude the Keyboard — MCP
05 What MCP Is Read first
In Stages 02–04 you were the courier. Claude wrote the code, you carried it to Grasshopper, ran it, and carried the error back. Claude never saw your model — it worked from your description of it.
MCP — Model Context Protocol — is an open standard for connecting an AI assistant directly to other software. An MCP server is a small adapter that sits beside a program and publishes what that program can do as a list of tools the assistant is allowed to call. Install the Rhino one and Claude can read your document, query object properties, build geometry, and capture the viewport to see what it made.
Same instructions, different channel. Part 1 is directing someone over the phone. MCP hands them the keyboard.
  • It is a standard, not a Claude feature. Servers exist for Blender, QGIS, Figma, spreadsheets, browsers. Learn the pattern once and it carries to all of them.
  • Everything runs on your machine. The server talks to Rhino locally; your model stays where it is.
  • You stay responsible for the output. Claude now edits your real document, so save before you start and check what changed.
The standard is young — published late 2024. Some servers are excellent, many are abandoned prototypes. Rhino’s is one of the good ones.
06 Install the Rhino Bridge RH SETUP
Four one-time steps, Windows or macOS. Then one command each time you open Rhino.
  • 1 · Claude Desktop. Install from claude.com/download. Same app WF07 uses — you are installing it a week early.
  • 2 · The Rhino plug-in. In Rhino 8: Tools → Package Manager, search rhinomcp, click Install, restart Rhino.
  • 3 · The launcher. The server runs through a tool called uv. Windows: winget install astral-sh.uv · macOS: brew install uv.
  • 4 · Register the server. Open Claude Desktop → Code tab → pick any folder, then paste the line below and let it do the wiring.
Please install https://github.com/jingcheng-chen/rhinomcp as a local MCP server named `rhino`.
To do step 4 by hand instead: Settings → Developer → Edit Config, and add —
{
  "mcpServers": {
    "rhino": {
      "command": "uvx",
      "args": ["rhinomcp@latest"],
      "env": {
        "RHINO_MCP_HOST": "127.0.0.1"
      }
    }
  }
}
⚠
Type mcpstart in Rhino's command line every session. That opens the bridge on port 1999. Restart Rhino and you type it again. Keep one MCP client connected at a time.
Confirm it works. Ask Claude "what's in my Rhino document?" — a correct answer lists your layers and object counts.
07 Run the Analysis Again — Claude Driving RH
Open your WF04 terrain, hand Claude the spec you wrote in Stage 02, and let it work in the document:
Read the surface on my Terrain layer. Analyze it against this spec, bake the result as a colored mesh on a new layer, then capture the perspective viewport and check whether the steep zones read correctly.
That last clause is the new move: Claude can look at its own output. It captures the viewport, sees the colors, and corrects itself before you have to describe the problem. A loop that closes on its own — which is the Week 11 lecture, running in front of you.
  • Save first. These edits land in your real file.
  • Name things precisely. "the surface on my Terrain layer" beats "my surface" — the same specification skill from Part 1, now with consequences.
  • Ask to see the code. The server can run RhinoScript-Python; ask Claude for the script it ran so you keep reading what you are shipping.
  • Two routes skip the copying, one does not. Claude can run Python inside Rhino directly, and it can assemble a Grasshopper canvas from stock components and wire it. Writing source into a Python 3 Script component stays manual — see What You Actually Installed below.
Worth noticing: which route did you understand better? Copy-paste made you read every line. This does not. Speed and comprehension pull against each other here — that tension is the point.
What You Actually Installed
Two questions sit behind this, and mixing them up is what makes MCP confusing. How does Claude know what Rhino can do? That is MCP — the protocol. How does a command actually reach Rhino? That is a plug-in. MCP is not the part doing the reaching; it is the layer that hands Claude the list of tools.
Which is why Stage 06 had you install two things, not one:
   Claude
     |  speaks MCP
   rhinomcp server    a program on your
     |                computer, started
     |                by Claude Desktop
     |  port 1999
   rhinomcp.rhp       a plug-in loaded
     |                INSIDE Rhino;
     |                mcpstart opens
     |                the port
   your model
.rhp is simply a Rhino plug-in — the same kind of thing as Human or Bowerbird, sitting in the same plug-in folder beside them. Neither half works alone: close Rhino and the server is still running but has nothing to talk to, which is why the connection dies the moment Rhino quits.
⚠
Grasshopper is the gap — and it is why Stages 03–04 still say copy and paste. The Rhino MCP has no tool for writing source into a Python 3 Script component, so the one step you might most want automated is the one that stays manual. Claude can build a Grasshopper canvas out of stock components and wire it, and it can run Python inside Rhino directly — but putting code into that component is still your hands on the keyboard.
A gap like that is rarely permanent and rarely accidental — it is a seam nobody has built across yet. Noticing where the seams are is most of what it takes to work with tools this young.
Other Software — Optional
MCP servers exist for AutoCAD, Blender, QGIS and plenty more. Almost all are written by the community rather than by the software vendors, and quality varies sharply — Rhino’s is one of the good ones. If you want to try another, search GitHub for the program’s name plus MCP, expect to do some repair work to get it running, and read the code with Claude before you trust it.
A note on COM. Rhino’s server gets in through a plug-in. Most servers for older programs, AutoCAD included, use COM instead — a Windows mechanism from the 1990s that lets one application drive another from outside, with nothing installed inside it. Convenient to set up, and more fragile: the version has to match and every value crosses a boundary where it can be misread. That is usually what you are repairing.
Tips
  • Slow down in the interview. Rushing past it skips the thinking.
  • A vague prompt gets a generic script. The model isn't the problem.
  • Describe what must be true when it works, not how the code should work.
  • Patch extends beyond your boundary. Tell Claude to exclude faces outside it — you don't need to know how, just that the problem exists.
  • In Part 2, judge the result by looking at the geometry, not by the tool saying it worked.
